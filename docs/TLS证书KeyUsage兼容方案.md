# 晓记账：TLS 证书 KeyUsage 兼容方案

| 项目 | 内容 |
| --- | --- |
| 技术决策编号 | T-051 |
| 日期 | 2026-07-30 |
| 当前状态 | 已选择并实现方案 1：省略不兼容的 `KeyUsage` 扩展 |
| 触发原因 | RSA 3072 证书可载入服务端，但带 `basic_utils 5.8.2` KeyUsage 扩展时被 Flutter/BoringSSL 客户端拒绝 |

## 新证据

首次真实 HTTPS 握手返回 `CANNOT_PARSE_LEAF_CERT`。使用同一把 RSA 3072 密钥逐项生成并握手测试后，结果如下：

| 证书内容 | Flutter/BoringSSL 真实握手 |
| --- | --- |
| 无扩展 | 通过 |
| SAN | 通过 |
| ExtendedKeyUsage | 通过 |
| BasicConstraints | 通过 |
| `basic_utils 5.8.2` KeyUsage | 失败 |

因此失败点是候选组件生成的 `KeyUsage` 编码，不是 RSA 3072、HTTPS、自签名证书或证书指纹固定本身。

## 方案 1：省略 KeyUsage 扩展（推荐）

继续使用 RSA 3072，保留 SAN、`SERVER_AUTH`、`CLIENT_AUTH`、`CA=false` 和 SHA-256 指纹固定，只不写入有兼容问题的 `KeyUsage`。

优势：真实握手已经通过；不新增依赖；改动最小；证书仍明确限定为 TLS 服务端和客户端用途，且不能作为 CA。

劣势：证书不再额外声明密钥的具体密码操作；约束主要由 App 代码、系统安全存储和 ExtendedKeyUsage 承担。

成本和风险：无新增费用，开发成本最低；晓记账私钥不会导出给其他功能，因此实际增加的风险较低。

## 方案 2：自行修复并维护 basic_utils

复制或修补候选组件的 ASN.1 `KeyUsage` 生成代码，使其符合 BoringSSL 接受的编码。

优势：可以保留全部预期证书扩展。

劣势：项目需要自行维护底层证书编码；上游升级时要长期合并和复测。

成本和风险：开发成本居中，密码学格式实现错误的安全风险最高。

## 方案 3：更换证书生成组件

引入另一个 Dart 证书库，或分别调用平台/OpenSSL 工具生成证书。

优势：有机会生成完整且标准的证书扩展。

劣势：新增供应链和跨平台差异；需要重新验证 Windows、macOS、Android 的密钥生成、安全存储、证书载入和握手。

成本和风险：开发和维护成本最高；可能重新引入平台安装依赖。

## 实现结果

- 设备证书继续使用 RSA 3072、SHA-256 签名、SAN、TLS 服务端/客户端 ExtendedKeyUsage 和 `CA=false`。
- 私钥继续只保存在系统安全存储，不进入二维码、备份、日志或同步载荷。
- HTTPS 客户端继续严格核对目标 IP、端口和证书 DER 内容的 SHA-256 指纹。
- 如果未来 `basic_utils` 修复该扩展或 Flutter/BoringSSL 行为变化，必须重新实测并按决策规则提案，不能静默改变证书格式。
- 正确指纹真实 HTTPS 握手、错误指纹拒绝、服务关闭拒绝连接和协议路由测试均已通过。
