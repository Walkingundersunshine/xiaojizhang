# 晓记账：汇率服务商与 API 密钥方案

| 项目 | 内容 |
| --- | --- |
| 决策编号 | T-024 |
| 调研日期 | 2026-07-29 |
| 当前状态 | 用户明确排除 API 密钥方案；无密钥来源转入 T-025 决策 |

## 1. 要决定什么

决定 App 从哪项服务获取历史汇率，以及第三方 API 密钥由谁提供和保管。

桌面安装包无法安全隐藏公共 API 密钥。把项目统一密钥直接写入 App 后，任何人都可能提取并消耗额度。因此首版要么由用户填写自己的密钥，要么额外建设服务器隐藏项目密钥。

## 2. 方案 1：Open Exchange Rates，用户填写自己的免费密钥（推荐）

根据其官方免费方案页面，当前提供：

- 每月 1,000 次 API 请求。
- 每日历史汇率。
- 支持本项目全部 12 种货币，包括 MOP 和 TWD。
- 免费方案以 USD 为基准，App 可以在本地精确交叉换算到用户选择的本位币。

优势：首版无服务器和固定费用；额度足够个人日常记账；货币覆盖完整；历史数据和文档成熟。

劣势：用户需要自行注册并把 API 密钥填入设置；依赖第三方服务条款；免费额度或规则未来可能变化。

密钥处理：只保存在本机，不上传到项目服务器；首版未启用数据库加密，因此需要明确提示密钥文件保护。

官方资料：[免费方案](https://openexchangerates.org/signup/free) · [支持货币](https://oxr.readme.io/docs/supported-currencies)

## 3. 方案 2：currencyapi.com，用户填写自己的免费密钥

根据其官方定价页面，免费方案当前提供：

- 每月 300 次请求。
- 每分钟最多 10 次请求。
- 支持历史汇率。

优势：免费方案明确包含历史数据；接口设计简洁；用户自己的密钥不会被其他用户共享消耗。

劣势：免费额度低于方案 1；仍需用户注册和填写密钥；需要在接入前用真实免费账户再次确认 MOP、TWD 的历史端点覆盖。

官方资料：[定价与额度](https://currencyapi.com/pricing/)

## 4. 方案 3：项目建设汇率中转服务器

App 连接本项目的服务器，服务器保存 Open Exchange Rates、ExchangeRate-API 等上游密钥并缓存历史汇率，用户无需填写密钥。

优势：使用体验最好；可统一缓存、切换上游服务并控制请求量；能避免密钥出现在桌面安装包。

劣势：需要服务器、域名、监控、安全更新和持续费用；服务器会看到用户请求的日期和币种；服务停止时所有用户受影响；当前项目尚未授权购买服务或部署服务器。

成本：高，并产生长期运维责任。

## 5. 不建议的方案

- Frankfurter/欧洲央行数据免费且无需密钥，但当前不提供 MOP 和 TWD，无法覆盖已经确定的 12 种货币。
- ExchangeRate-API 的公开无密钥接口覆盖全部 12 种货币，但只提供最新汇率；其官方历史接口当前仅对付费账户开放，不能单独满足“历史汇率”选择。
- 不应把一个统一的免费密钥直接硬编码进桌面 App。

## 6. 我的建议

建议选择 **方案 1：Open Exchange Rates + 用户自己的免费密钥**。它在完整货币覆盖、历史数据、免费额度和无需服务器之间最平衡。

实现后，App 会按花销日期缓存每日汇率，离线时优先使用已缓存数据；汇率请求失败不会修改或损坏原始账目金额。
