# 晓记账：本地数据加密方案

| 项目 | 内容 |
| --- | --- |
| 决策编号 | T-006 |
| 日期 | 2026-07-29 |
| 当前状态 | 已选择方案 1：首版不加密 |

## 1. 要决定什么

决定保存在电脑上的账目数据库是否加密，以及用户打开 App 时如何取得解密密钥。

## 2. 为什么现在要决定

账目包含金额、时间、分类和备注，属于敏感个人信息。加密方式会影响 SQLite 运行库、启动流程、备份恢复和密码遗失风险，必须在创建数据库之前确定。

## 3. 方案 1：首版不加密，依赖系统账户保护

做法：数据库保持普通 SQLite 文件，依赖 Windows/macOS 登录账户、文件权限以及用户自行启用的磁盘加密功能保护。

优势：

- 实现最简单、稳定性最高。
- 不需要密码，也不存在忘记密码后永久无法恢复账目的风险。
- 备份、恢复和跨电脑迁移最容易。
- 保持当前标准 SQLite 运行库，不增加第三方加密组件。

劣势和风险：

- 得到数据库文件的人可以使用 SQLite 工具直接读取账目。
- 共用电脑、恶意软件或未加密备份可能暴露财务信息。
- 以后增加加密时需要执行一次数据库迁移。

成本：低。

## 4. 方案 2：数据库加密，使用用户密码解锁

做法：使用兼容 SQLite 的加密运行库，用户设置独立密码，每次打开 App 时输入密码解锁。

优势：

- 数据库文件和普通备份即使被复制，也不能直接读取。
- 密钥由用户掌握，不完全依赖当前电脑账户。
- 适合对财务隐私要求高或经常复制备份的用户。

劣势和风险：

- 忘记密码时无法恢复数据，App 也不能替用户找回。
- 每次打开需要输入密码，使用步骤增加。
- 需要额外加密运行库，并审核其许可证和 Windows/macOS 兼容性。
- 密码修改、加密备份和异常恢复都需要更多开发与测试。

成本：高。

## 5. 方案 3：数据库加密，密钥保存在系统保险箱（推荐）

做法：使用兼容 SQLite 的加密运行库；随机密钥由 App 生成，Windows 保存到凭据管理器，macOS 保存到钥匙串，正常使用时自动解锁。

优势：

- 数据库文件被单独复制后无法直接读取。
- 用户日常无需输入额外密码，体验接近未加密方案。
- 使用两个系统已有的安全存储能力，不把明文密钥放进数据库旁边。

劣势和风险：

- 用户已登录并能运行 App 时，保护能力弱于每次输入独立密码。
- 只复制数据库文件不能在新电脑恢复，备份功能必须同时设计安全的密钥导出或由 App 导出数据。
- 重装系统或系统保险箱损坏可能导致数据无法解密，因此备份恢复设计必须更加谨慎。
- 需要额外加密库和安全存储插件，开发、测试和长期维护成本高于方案 1。

成本：中到高。

## 6. 我的建议

建议选择 **方案 3：数据库加密，密钥保存在系统保险箱**。账目属于敏感信息，这个方案能避免数据库文件被直接读取，同时不要求用户每天输入密码。

需要接受的代价是：后续备份功能必须由 App 统一完成，不能把数据库文件简单复制到另一台电脑就直接使用。正式采用前还会单独给出加密运行库和安全存储组件的选型方案，不会擅自增加依赖。

如果首要目标是尽快完成可用的首版，并且电脑仅由本人使用，方案 1 也合理；但其隐私保护明显较弱。
