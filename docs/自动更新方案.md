# 晓记账：自动更新方案

| 项目 | 内容 |
| --- | --- |
| 决策编号 | T-008 |
| 日期 | 2026-07-30 |
| 状态 | 已选择方案 1：首版不提供自动更新 |
| 影响范围 | App 联网行为、发布服务器、更新安全、使用便利和维护成本 |

## 背景

当前 Windows 包是无签名内部测试版，没有固定下载服务器，也没有代码签名。自动更新不仅是“下载新版本”，还必须确认下载来源、校验文件、防止更新中断损坏程序，并分别处理 Windows 和 macOS 的安装机制。

汇率联网与软件更新是两件独立的事情。即使 App 已允许联网获取汇率，也不能自动推断用户同意它后台检查或安装软件更新。

## 方案 1：首版不提供自动更新（推荐当前阶段）

- App 不在后台检查版本，也不下载或替换程序文件。
- 新版本由用户手动取得，使用 `.jizhang` 备份迁移数据。
- 设置页可显示当前版本，但不增加联网检查按钮。

优势：没有更新服务器和证书成本；不会增加后台联网；不存在自动更新被劫持或失败损坏安装的风险；最符合当前无签名内部测试包定位。

劣势：用户必须自己关注并下载新版本；测试者可能继续使用旧版本；发布说明需要明确升级步骤。

## 方案 2：只检查和提示，不自动安装

- App 手动或定期读取一个 HTTPS 版本清单。
- 发现新版本后显示版本号、更新说明和下载链接，由用户自行下载。
- 版本清单需包含平台、文件地址、大小和 SHA-256。

优势：比完全手动更容易发现更新；App 不直接替换自身，失败风险低于完整自动更新；可以逐步建立发布基础设施。

劣势：需要长期稳定的 HTTPS 托管位置；仍然存在新增联网和隐私说明；必须保护版本清单和下载链接；用户仍需手动安装。

## 方案 3：完整自动下载并安装

- App 检查新版本、下载、验证签名或哈希，然后退出并由独立更新程序替换文件。
- Windows 和 macOS 分别处理权限、正在使用的文件、签名、公证和失败回滚。

优势：用户升级最方便；容易让大规模用户保持在较新版本；可以及时推送重要修复。

劣势：安全和实现复杂度最高；需要可信服务器、签名、独立更新程序和失败回滚；无签名便携包下容易被系统拦截；两套桌面平台必须分别测试。

## 建议

当前建议选择方案 1。内部测试阶段先保持无后台更新，版本升级通过新的 ZIP 完成。等未来确定签名与公开发布渠道后，再重新评估方案 2 或方案 3，避免现在引入与发布基础设施不匹配的安全风险。
