# 晓记账：花销时间保存方案

| 项目 | 内容 |
| --- | --- |
| 决策编号 | T-022 |
| 日期 | 2026-07-29 |
| 当前状态 | 已选择并实现方案 2 |

## 1. 要决定什么

决定每笔花销的发生日期和时间如何保存，尤其是用户旅行或电脑时区变化时，历史记录应如何显示。

## 2. 为什么现在要决定

产品包含海外旅行和多货币记账场景。时间保存方式会影响按天筛选、月度统计、排序，以及用户回到另一个时区后看到的历史日期。

## 3. 方案 1：只保存 UTC 绝对时间

做法：所有时间统一换算为世界标准时间保存，显示时使用电脑当前时区。

优势：

- 不同地区产生的记录可以准确按先后顺序排序。
- 实现成熟，系统日志和同步功能通常采用这种方式。
- 未来增加云同步较方便。

劣势和风险：

- 用户回国或更改电脑时区后，历史花销的显示时间会改变。
- 接近午夜的记录可能变成前一天或后一天，月度统计也可能变化。

成本：低。

## 4. 方案 2：保存 UTC 时间和记录时的时区偏移（推荐）

做法：同时保存世界标准时间和记账当时的时区偏移。例如在东京记录时，保存绝对时间以及 `+09:00`。

优势：

- 可以准确排序，也能始终还原用户记账时看到的当地日期和时间。
- 回国后历史记录不会因为电脑时区变化而跳到另一天。
- 适合海外旅行、多货币和未来同步场景。

劣势和风险：

- 数据库多保存一个很小的时区偏移字段。
- 输入、显示和日期筛选逻辑比方案 1 多一步转换。
- 只能还原当时的偏移量，不能完整记录具体城市时区名称；对记账场景通常足够。

成本：中等。

## 5. 方案 3：只保存用户输入的本地日期和时间

做法：数据库保存“2026-07-29 20:00”这样的本地时间，不记录它属于哪个时区。

优势：

- 历史记录显示永远不变。
- 按用户看到的日期进行筛选和统计最直接。
- 实现简单。

劣势和风险：

- 在不同时区产生的记录无法准确比较真实先后顺序。
- 夏令时切换时可能出现重复或不存在的时间。
- 未来增加云同步、自动导入或跨设备使用时迁移成本较高。

成本：低，但长期扩展风险较高。

## 6. 我的建议

建议选择 **方案 2：保存 UTC 时间和记录时的时区偏移**。它既能准确排序，也能保证旅行期间的账目日期回国后不变化，最符合本产品的多货币旅行场景。

创建时间和更新时间属于系统审计信息，不需要保留用户看到的当地时间，将统一保存为 UTC。
