# 晓记账：自定义分类标识方案

| 项目 | 内容 |
| --- | --- |
| 决策编号 | T-023 |
| 日期 | 2026-07-29 |
| 当前状态 | 已选择并实现方案 1：UUID v4 |

## 1. 要决定什么

决定用户新增分类时，App 如何生成数据库内部标识。用户界面不会显示该标识，但每笔历史账目都通过它关联分类。

## 2. 方案 1：UUID v4 随机标识（推荐）

示例：`b91c2bb7-3d62-4f5e-92a1-13dbd61b8d31`。

优势：几乎不会重复；不同电脑创建的数据未来可以合并；成熟且跨平台。

劣势：标识较长、不便人工阅读；需要增加一个很小的 UUID 生成依赖。

成本：低。

## 3. 方案 2：数据库自增整数

示例：`101`、`102`、`103`。

优势：短、查询和调试直观；SQLite 原生支持，不需要新依赖。

劣势：不同电脑会生成相同编号，未来备份合并或云同步容易冲突；当前系统默认分类已经使用文本标识，数据库结构需要改为双轨或整体迁移。

成本：当前中等，未来同步迁移成本高。

## 4. 方案 3：ULID 可排序标识

示例：`01K1B4J8K3R5F7M9N2Q6T8V0WX`。

优势：全局唯一，并且按生成时间大致可排序；比 UUID 更适合查看创建顺序。

劣势：生态和通用程度低于 UUID；分类顺序仍应使用单独的排序字段，因此其可排序优势对本项目有限；需要额外依赖。

成本：低到中。

## 5. 我的建议

建议选择 **方案 1：UUID v4**。当前分类表已经使用文本标识，UUID 可以直接兼容现有结构，并为未来备份合并或多设备同步预留空间。分类显示顺序继续使用独立的 `sortOrder` 字段，不依赖标识本身。
