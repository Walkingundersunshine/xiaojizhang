## 所有方案共同遵守

- 日志放在 App 私有数据目录，不和账本数据库放进用户手动选择的导出位置。
- 不记录金额、备注、分类名称、备份正文或完整用户文件路径。
- Windows 盘符路径、macOS 用户目录等内容在写入前脱敏。
- 捕获 Flutter 界面错误和未处理的异步异常；普通操作成功不大量写日志。
- 设置页提供“导出诊断日志”，每次使用系统“另存为”窗口，由用户主动保存。

## 方案 1：`logging` + JSON Lines，最多 5 MB（推荐）

- 使用 Dart 生态中轻量、成熟的 `logging` 包管理日志级别和来源。
- 每条记录为一行 JSON，包含 UTC 时间、级别、功能来源、错误类型、脱敏消息和脱敏堆栈。
- 单个文件达到 1 MB 时轮换，最多保留 5 个文件，总上限约 5 MB。
- 导出时把现有记录按时间整理成一个 `.jsonl` 文件。

优势：结构稳定，开发者和诊断脚本都容易分析；日志来源和级别清楚；容量足以保留近期问题；依赖轻量，不加入第三方联网服务。

劣势：需要自行实现文件轮换和路径脱敏；普通用户直接打开 JSON Lines 不如纯文本直观；新增一个运行依赖。

## 方案 2：完全自写纯文本日志，最多 1.5 MB

- 不增加日志包，直接写入时间、级别和错误摘要。
- 单文件 512 KB，最多保留 3 个文件。
- 导出为一个普通 `.log` 文本文件。

优势：依赖最少；文件容易用记事本查看；磁盘占用更小。

劣势：日志级别、来源和格式都要自行维护；后续做自动分析更困难；容量较小，频繁错误时旧线索更快被覆盖。

## 方案 3：社区完整日志框架，最多 10 MB

- 使用 `talker_flutter` 等社区框架，获得日志查看器、过滤、异常展示等功能。
- 保留更长时间的日志，并可在 App 内查看。

优势：诊断功能最丰富；开发阶段查看方便；后续扩展网络请求追踪更容易。

劣势：新增依赖和代码范围最大；App 内日志查看器会增加界面复杂度；必须额外确保框架不会自动记录敏感对象；对当前个人记账首版偏重。

## 建议

建议选择方案 1。约 5 MB 的上限对桌面设备影响很小，JSON Lines 便于准确排错，同时仍保持完全本地、用户主动导出的隐私边界。

## 实现与验证结果

- 使用 `logging 1.3.0`，活动日志为 `jizhang-0.jsonl`，按 1 MB 轮换并最多保留 5 个文件。
- App 启动时捕获 Flutter 框架异常、平台异步异常和 Zone 未处理异常；日志初始化失败不会阻止 App 启动。
- 任意异常对象正文不直接写入，只记录错误类型；消息由代码提供固定安全说明。
- Windows、macOS 用户目录和绝对文件路径在堆栈写入前替换为 `<path>`。
- 设置页新增“导出诊断日志”，导出为按时间排列的单个 `.jsonl` 文件，不自动上传。
- 脱敏、异常正文排除、轮换和导出顺序测试通过；全部 35 项自动测试通过。
- Windows Debug/Release 构建通过；Release 实际启动后在 App 私有目录成功生成 JSONL 启动日志。
- Windows Release 人工验收通过：“导出诊断日志”按钮可见，系统“另存为”窗口正常打开。
