## 背景

当前 Windows Debug 程序适合开发测试，但不是交付给普通用户的正式安装包。Windows 和 macOS 都会检查从网络下载的软件是否可信；代码签名可以证明发布者并降低安全警告，但需要证书、开发者账户和持续维护。

macOS 正式包必须在一台 macOS 电脑上编译、签名和验证，当前 Windows 电脑不能代替这一步。

## 方案 1：先制作无签名内部测试包，公开发布前再决定签名（推荐当前阶段）

- Windows 生成 Release 版便携目录并打成 ZIP，解压后运行。
- macOS 日后在 Mac 上生成 `.app` 测试包并压缩。
- 仅自己或少量可信测试者使用，不把它当成公开正式版。

优势：目前不需要购买证书或开发者账户；最快验证 Release 性能、数据库位置、备份和跨平台行为；后续仍可升级为签名安装包。

劣势：从网络下载后，Windows 可能显示 SmartScreen 提示；macOS Gatekeeper 可能阻止直接打开；没有系统安装、卸载和可信发布者体验；不适合大范围分发。

成本：通常无直接费用，但仍需要一台 Mac 完成 macOS 构建测试。

## 方案 2：直接准备官网式签名安装包

- Windows 制作 MSIX 或安装程序并使用代码签名证书。
- macOS 制作签名、Apple 公证的 DMG 或 PKG。
- 用户从自有网站、网盘或其他渠道下载。

优势：安装体验专业；显著减少未知发布者和 Gatekeeper 警告；发布渠道可自行控制；不必等待应用商店审核。

劣势：需要购买和维护 Windows 代码签名证书；需要 Apple Developer 账户及 Mac；证书续期、签名、公证和密钥保护都要建立流程；自动更新仍需另行决定。

成本：Apple Developer Program 通常需要按年付费；Windows 证书价格取决于证书类型和供应商，购买前需要再次核对当时价格与身份验证要求。

## 方案 3：通过 Microsoft Store 和 Mac App Store 发布

- 分别注册微软和 Apple 开发者账户，使用商店要求的包格式、签名和审核流程。

优势：用户信任度高；安装、卸载和更新体验统一；商店负责主要分发；签名与发布身份更规范。

劣势：需要开发者账户、费用和审核时间；必须遵守两个商店不同的政策；macOS 沙盒可能影响文件访问等桌面能力，需要额外适配和测试；每次发布受审核流程影响。

成本：需要相应开发者账户，具体费用和政策在真正注册前应以微软、Apple 官方当前信息为准。

## 建议

当前建议选择方案 1：先形成可复现的 Windows Release 内部测试包，并在有 Mac 后完成 macOS 实机验证。等功能、数据迁移和性能稳定后，再由你决定选择官网签名发布还是应用商店发布，避免现在就产生证书费用和账户负担。

无论选择哪一项，都不会在未经你确认的情况下购买证书、注册账户或向外部渠道上传 App。
