## 1. 用户对技术决策方式的明确要求

用户在整个项目开发过程中不负责提出具体技术实现要求。所有技术事项必须遵循以下协作规则：

1. 助手发现需要技术选择时，主动识别并提出该决策，不能把问题简单抛给用户。
2. 助手为每个重要技术问题提供多个可行方案，通常为 2～3 个；如果实际上只有一个合理方案，需要解释原因。
3. 每个方案必须使用非专业用户可以理解的语言说明“它是什么”。
4. 每个方案必须说明与产品有关的优势、劣势、成本和风险，不能只罗列技术名词。
5. 助手可以给出明确推荐，并说明推荐依据，但推荐不等于最终决定。
6. 最终采用哪个方案由用户决定。用户没有明确选择前，助手不得把某一方案记录为“已确定”或据此进行大规模、难以撤销的开发。
7. 对安全、隐私、数据丢失、费用、第三方服务依赖、跨平台兼容和长期维护有影响的事项，必须特别指出。
8. 当一个决策会影响已完成内容、开发周期或未来迁移成本时，助手必须在实施前解释影响。
9. 用户作出选择后，助手要把选择、理由、日期和影响写入本文件的“决策记录”。
10. 如果后续出现新证据，助手应说明是否建议重新决策，不能在没有告知用户的情况下偷偷替换技术方案。

### 1.1 每次向用户提案时的固定格式

以后所有重要技术决策均按以下结构沟通：

- 要决定什么：用一句话说明问题。
- 为什么现在要决定：说明它会影响哪些功能或工作。
- 方案 A / B / C：用日常语言解释每个方案。
- 优势与劣势：包括用户体验、开发速度、安装包大小、性能、稳定性、维护成本等相关因素。
- 我的建议：给出推荐和理由。
- 你的选择：明确等待用户作出最终决定。

### 1.2 哪些事项必须让用户决定

至少包括但不限于：

- 桌面应用技术栈和主要框架。
- 数据保存在本地还是云端。
- 是否使用收费服务或可能产生持续费用的第三方服务。
- 是否建立账号、登录和云同步。
- 汇率来源以及是否允许联网获取汇率。
- 自动更新、崩溃报告、使用情况统计等可能联网或收集信息的功能。
- 数据备份、加密和恢复策略。
- 会显著影响安装包大小、启动速度、系统兼容或未来维护成本的选择。

日常代码命名、格式化、测试文件组织等低风险且可轻易修改的实现细节，可以由助手按行业惯例处理，但应保证不违背已经确定的方案。

## 2. 首次技术选型：跨平台桌面技术栈

目前需要先决定用什么技术构建 Windows 和 macOS 应用。下面三种方案都可实现需求，但侧重点不同。

### 方案 A：Tauri + React + TypeScript + SQLite

通俗解释：界面使用成熟的网页界面技术开发，Tauri 把它包装成真正的桌面应用；SQLite 是保存在电脑本地的单文件数据库。Tauri 的底层核心使用 Rust，但大部分产品界面与业务逻辑可以用 TypeScript 编写。

优势：

- Windows 和 macOS 可以共用绝大多数代码。
- 安装包通常比 Electron 小，占用内存通常也更低。
- 适合本地数据和隐私优先的记账工具。
- React、TypeScript 和 SQLite 生态成熟，后续人员较容易接手。
- Tauri 对可调用的系统能力采用较严格的权限配置，安全边界较清晰。

劣势：

- 涉及安装、系统菜单、文件权限或数据库插件时，需要理解少量 Rust 和 Tauri 配置。
- 不同系统使用各自内置的网页渲染组件，偶尔会出现平台显示差异，需要分别测试。
- 相比 Electron，桌面插件数量和疑难问题资料略少。
- macOS 正式分发仍需要苹果开发者签名和公证流程。

适合：重视安装包体积、运行资源、本地数据与长期维护，希望界面现代且愿意进行充分跨平台测试。

### 方案 B：Flutter + Dart + SQLite

通俗解释：Flutter 使用自己的界面绘制方式，同一套代码直接绘制 Windows 和 macOS 界面；主要开发语言是 Dart，本地数据仍使用 SQLite。

优势：

- 两个平台的界面表现通常更一致。
- 动画、图表和自定义界面的表现好。
- 一套技术以后可以较自然地扩展到 Android 和 iOS。
- 性能通常较好，不依赖网页界面框架。

劣势：

- 桌面端生态和部分系统集成插件不如网页生态成熟，需要认真验证。
- 安装包通常大于 Tauri。
- Dart 的开发人才和第三方资料少于 JavaScript/TypeScript。
- Flutter 风格控件如果不额外适配，可能不像 Windows 或 macOS 原生应用。

适合：未来较可能开发手机端，或特别重视跨平台视觉一致性、动画和图表体验。

### 方案 C：Electron + React + TypeScript + SQLite

通俗解释：Electron 会把一套完整的网页运行环境和 App 一起打包。许多知名桌面软件使用它，界面开发仍采用 React 和 TypeScript，本地数据库使用 SQLite。

优势：

- 技术成熟，教程、插件和问题解决资料最多。
- Windows 和 macOS 共用代码的程度高，显示差异通常较少。
- 开发和调试速度快，寻找熟悉该技术的开发者相对容易。
- 桌面菜单、快捷键、托盘、自动更新等常见能力方案丰富。

劣势：

- 安装包明显更大，通常也会占用更多内存。
- 对功能相对聚焦的记账应用来说，运行环境偏重。
- 必须严格隔离界面和系统权限，否则容易引入安全风险。
- 随着 Electron 和内置浏览器版本更新，需要持续跟进安全升级。

适合：最重视开发成熟度、生态和交付速度，并能接受较大安装包与较高资源占用。

## 4. 首次提案时的推荐

助手当前推荐 **方案 A：Tauri + React + TypeScript + SQLite**。

推荐理由：

1. “晓记账”首版是功能聚焦、本地数据为主的桌面工具，Tauri 的轻量特征与产品形态匹配。
2. React 和 TypeScript 适合快速制作清晰的表单、列表、筛选和统计界面。
3. SQLite 不需要用户另行安装数据库，适合可靠保存大量本地账目。
4. Windows 和 macOS 可以共用大部分代码，同时保留访问本地备份、导出和系统能力的空间。
5. 与 Electron 相比，可望获得更小的安装包和更低的日常资源占用。

需要用户特别权衡的一点：如果未来很快就要开发 iPhone 和 Android 版本，那么方案 B（Flutter）的长期复用优势可能比方案 A 更重要；如果最优先目标是用最成熟的桌面生态快速开发，且不在意安装包大小，则方案 C（Electron）更稳妥。

以上内容是作出决定前的推荐背景。用户已于 2026-07-29 明确选择方案 B，因此最终实施方向为 **Flutter + Dart + SQLite**。

### 4.1 用户最终选择：方案 B

已确定的技术栈：

- 使用 Flutter 构建 Windows 和 macOS 桌面界面。
- 使用 Dart 编写界面与业务逻辑。
- 使用 SQLite 在用户电脑上保存账目数据。
- Windows 和 macOS 尽量共用同一套业务代码。

该选择带来的主要影响：

- 两个平台较容易保持一致的界面与交互。
- 如果以后增加 Android 或 iOS 版本，部分界面和业务代码有较好的复用机会。
- 开发过程需要使用 Flutter、Dart 及相应的桌面端插件。
- 安装包预计会大于 Tauri 方案，但通常仍小于或接近 Electron 方案的量级；实际大小需要在构建后测量。
- 文件导出、系统菜单、安装与自动更新等桌面能力，需要分别验证 Flutter 插件在 Windows 和 macOS 上的稳定性。
- macOS 正式发布仍需要处理苹果开发者签名和公证流程。

用户没有说明选择 B 的具体理由，因此决策记录只保存明确选择，不代替用户推测原因。

## 5. 三种方案都会采用的数据库建议

无论选择哪种界面技术，当前建议首版本地使用 SQLite：

- 它无需用户安装或维护服务器。
- 所有账目可以可靠地存放在本机数据库文件中。
- 支持筛选、统计和 10 万级以上记录查询。
- 方便制作备份、恢复和数据迁移。
- 应使用数据库迁移机制，使以后升级 App 时可以安全更新数据结构。

用户选择的方案 B 已包含 SQLite，因此本地数据库方向同时确定。具体使用哪个 Flutter 数据库访问库、如何迁移数据库版本，仍属于后续技术决策，需要另行提供方案。
