## 要决定什么

选择电脑端生成二维码和 Android 端调用相机扫描二维码的 Flutter 组件。

## 方案 1：`qr_flutter` + `mobile_scanner`（推荐）

电脑端用纯 Flutter 的 `qr_flutter` 绘制二维码；Android 端用 `mobile_scanner` 调用 CameraX/ML Kit 扫码。当前版本分别为 `4.1.0` 和 `7.4.0`。

优势：扫码组件更新活跃，支持当前 Flutter；Android 使用 Google CameraX/ML Kit，识别能力和相机兼容性较成熟；二维码生成不需要联网；API 和社区资料较多。

劣势：ML Kit 和相机原生组件会增加 Android APK 体积；需要 Android 相机权限；`qr_flutter` 最近正式发布时间较早，虽然功能简单稳定，仍需锁定版本并测试。

成本和风险：组件免费；开发成本最低；必须限制只解析晓记账自有格式，并在解析前检查长度和字段，不能把二维码内容当作任意链接打开。

## 方案 2：`qr` + `qr_code_scanner_plus`

电脑端使用 Dart `qr 4.0.0` 生成二维码数据并自行绘制，Android 端使用 `qr_code_scanner_plus 2.2.0` 的 ZXing 扫描实现。

优势：两个组件近期都有更新；ZXing 技术成熟；不依赖 ML Kit 扫描流程。

劣势：电脑端需要自己处理二维码绘制或再增加绘制代码；扫描组件生态和资料少于 `mobile_scanner`；仍需相机权限和 Android 原生兼容测试。

成本和风险：组件免费；开发成本居中；自绘二维码需要额外验证尺寸、容错级别和高 DPI 显示。

## 方案 3：三个平台分别实现原生二维码功能

Windows/macOS 使用各自图形库生成，Android 使用原生 CameraX/ML Kit 或 ZXing，通过平台通道与 Flutter 通信。

优势：平台控制最细；可以针对每个系统优化相机和图像处理。

劣势：需要 C++、Swift、Kotlin 三套代码；维护和实机测试量最大；对当前简单二维码配对明显过重。

成本和风险：开发成本最高；平台差异可能导致二维码载荷解析规则不一致。

## 我的建议

建议选择方案 1。`mobile_scanner` 对当前 Flutter 和 Android CameraX 支持活跃，`qr_flutter` 只负责本地绘制，组合成熟且实现工作最少。

## 三种方案共同要求

- 二维码仅在本地生成和扫描，不上传图片或扫码内容。
- Android 相机权限只在用户进入扫码页并主动开始时请求。
- 没有相机、权限被拒绝或扫码失败时提供手动短码入口。
- 二维码短时过期，解析时验证格式版本、字段长度、IP/端口、证书指纹和一次性令牌。
- 扫描器只接受晓记账配对格式，不自动打开 URL 或执行二维码中的其他内容。
