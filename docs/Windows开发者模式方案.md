## 1. 为什么遇到这个问题

Flutter 桌面插件会在工程的临时目录中创建“符号链接”，让 Windows 工程引用插件源码。当前项目加入 `path_provider` 后，Flutter 在创建插件链接时被 Windows 拒绝，并提示启用 Developer Mode。

目前已成功写入的依赖包括：

- `flutter_riverpod` 3.3.2。
- `drift` 2.34.2。
- `sqlite3` 3.5.0。
- `path` 1.9.1。
- `path_provider` 2.1.6。

开发依赖 `drift_dev` 和 `build_runner` 尚未继续安装，避免在权限问题未决定前产生更多不完整状态。

## 2. 方案 1：启用 Windows 开发者模式

做法：在当前 Windows 系统中开启 Developer Mode，使普通开发进程可以创建符号链接。

优势：

- 是 Flutter 官方提示的标准解决方法。
- VS Code、Flutter 和插件构建可以在普通权限下运行。
- 以后加入文件选择、窗口管理等其他桌面插件时无需重复处理。
- 不需要每次使用管理员身份运行开发工具。

劣势：

- 这是 Windows 系统级设置，不只影响当前项目。
- 会开放面向开发的部分能力，例如更宽松的应用旁加载和符号链接创建。
- 需要用户明确同意，不能默认开启。

## 3. 方案 2：每次使用真正提升权限的终端构建

做法：保持开发者模式关闭，所有需要插件符号链接的 Flutter 命令都在管理员提升权限的终端中运行。

优势：

- 不开启 Windows 开发者模式。

劣势：

- 每次开发、构建和更新插件都可能需要管理员授权。
- 让构建脚本获得较高系统权限，长期风险反而更大。
- VS Code 普通窗口与管理员构建生成的文件容易产生所有权和权限不一致。
- 当前自动化环境无法保证每个构建子进程都获得真正的 UAC 提升权限。

## 4. 方案 3：移除所有 Flutter 桌面插件

做法：移除 `path_provider` 等插件，手工为 Windows 与 macOS 分别实现数据目录和系统能力。

优势：

- 当前阶段可能避开插件符号链接。
- 不更改 Windows 设置。

劣势：

- 增加大量平台专用代码，降低 Windows/macOS 共用程度。
- 以后增加导出、文件选择或窗口功能时仍会遇到插件需求。
- 与已经选择的轻量、可维护架构相冲突。
- 不能保证所有 SQLite 原生依赖都永远不需要开发者链接能力。

## 5. 我的建议

建议选择 **方案 1：启用 Windows 开发者模式**。

这是 Flutter Windows 开发的标准环境设置，只需配置一次。为了降低风险，项目仍只使用经过确认的依赖，不运行来源不明的 MSIX 或脚本。
