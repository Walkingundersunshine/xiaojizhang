## 要决定什么

首次配对后，App 需要长期保存对方的公开证书、证书指纹、显示名称、配对时间、最后同步时间和撤销状态。这里决定这些非秘密的设备信任信息保存在哪里；本机身份私钥仍按 T-044 保存在系统安全存储，不属于本次选择范围。

## 方案 1：SQLite 独立设备表（推荐）

在现有 Drift/SQLite 数据库中增加 `paired_devices` 独立表，以设备 ID 为主键，保存对方公开证书和信任状态。通过独立 Repository 统一执行新增信任、查询活动设备、记录最后同步时间和撤销操作。

优势：结构化查询、排序和状态更新最清楚；可在同一事务中检查重复证书和设备 ID；数据库迁移与现有 Drift 架构一致；撤销记录可以保留以避免误恢复信任；适合后续设置页设备列表和监听信任集合。

劣势：表与账本数据位于同一个 SQLite 文件，必须在备份与恢复代码中明确排除；数据库升级需要增加迁移和回归测试；设备增删后仍需额外触发 mTLS 监听环境重建。

成本和风险：开发成本居中；主要风险是误把设备信任当作账本内容备份或恢复，因此必须用测试固定边界。

## 方案 2：系统安全存储

将对方公开证书和设备元数据与本机私钥一起保存到 Windows、macOS 和 Android 的系统安全存储。

优势：与身份凭据集中保存；天然不会进入 SQLite 账本备份；其他普通应用文件不可直接读取。

劣势：公开信息并不需要凭据级保护；列表查询、排序、撤销记录和结构迁移不适合键值型安全存储；跨平台行为和容量限制更难统一；设置页设备列表实现更复杂。

成本和风险：跨平台测试成本较高；大量结构化元数据放入安全存储会增加维护难度，且不能替代 SQLite 的查询能力。

## 方案 3：App 私有目录中的独立 JSON 文件

在应用私有数据目录维护一个版本化 JSON 文件，保存所有已配对设备的公开信息和撤销状态。

优势：与账本数据库物理分开；备份边界直观；无需为设备信息升级数据库版本。

劣势：并发更新、原子写入、损坏恢复、字段迁移和查询都需要自行实现；文件部分写入可能丢失整份信任列表；长期可靠性不如 SQLite。

成本和风险：初始代码量不高，但需要补充临时文件、原子替换和损坏恢复机制，长期维护成本偏高。

## 我的建议

建议选择方案 1。已配对设备是结构化、可查询、会更新和会撤销的数据，SQLite 更适合承担这类状态；通过备份测试明确排除该表，可以同时保持账本可迁移与设备信任不随备份复制。

## 已确定的实现规则

- 数据库从 schema v3 升级到 v4，迁移只新增 `paired_devices` 表，不改变现有账本和设置。
- 表内保存设备 ID、显示名称、对方公开证书 PEM、证书 SHA-256 指纹、配对时间、最后同步时间、撤销状态和撤销时间。
- 只保存对方公开证书，不保存对方私钥；本机证书私钥继续只保存在系统安全存储。
- 同一公开证书不能属于另一设备；同一设备 ID 不能静默更换证书，证书变化时必须作为新设备重新配对。
- 移除设备采用保留撤销记录的方式；活动信任查询立即排除已撤销设备，避免旧证书继续进入 mTLS 白名单。
- `paired_devices` 不进入 CSV、`.jizhang` 完整备份、恢复前安全备份或恢复操作；恢复账本不能新增、覆盖、删除或重新启用设备信任。
- 新增、重新信任或撤销设备后，后续网络接入层必须关闭旧监听，并使用最新活动证书集合重建 mTLS 监听环境。
- 本次数据层实现同时修复默认本位币设置未固定 `id=1` 的旧缺陷，防止数据库重启后因 SQLite 自动编号产生重复设置行。
