## 要决定什么

首次配对完成后，手机再次发起同步时，如何向电脑证明自己仍是已配对设备，而不是同一局域网内的其他设备。

## 方案 1：双向 TLS 证书认证（推荐）

手机验证电脑二维码或已保存的证书指纹；电脑同时要求手机在 TLS 握手中出示首次配对时保存的设备证书。双方都需要证明持有各自系统安全存储中的私钥。

优势：使用成熟 TLS 标准，不自行设计签名消息；证书与已有 RSA 3072 身份和系统安全存储决定一致；未配对设备在读取 HTTPS 内容前就会被拒绝。

劣势：电脑必须在启动监听前加载当前受信任设备证书；新增或移除设备后需要关闭并重新建立监听环境。

成本和风险：不增加第三方服务或费用，开发成本居中；必须同时进行 TLS 证书链校验和应用内精确指纹白名单校验，不能只信任同一名称的证书。

## 方案 2：每次请求使用手机私钥签名

HTTPS 只验证电脑身份，手机对请求正文、时间戳和随机数签名，电脑使用配对时保存的手机公钥验证。

优势：新增或移除设备不需要重建 TLS 监听环境；可以为每条请求留下明确签名结果。

劣势：需要自行定义规范化正文、时间戳容差、随机数和防重放缓存；不同平台序列化差异可能造成签名不一致。

成本和风险：无服务费用，但协议设计和安全测试成本高；自定义防重放实现错误可能允许旧请求再次提交。

## 方案 3：长期共享密钥

首次配对后两端保存同一个高强度随机秘密，以后每次请求携带基于该秘密的认证信息。

优势：实现最简单，验证速度快，不依赖客户端证书握手。

劣势：两端都保存同一个可冒充设备的秘密；撤销、复制和备份边界比公开证书身份更难解释，也不能充分利用已经生成的设备私钥。

成本和风险：开发成本最低，但长期秘密泄露后的冒充风险最高。

## 已确定的实现规则

- 首次配对阶段仍使用二维码/六位短码和一次性令牌，不强制已有客户端证书。
- 后续同步监听环境必须加载当前所有已配对设备的公开证书，并请求客户端证书。
- 手机 HTTPS 客户端从系统安全存储加载自己的证书和私钥，同时继续严格固定电脑证书 SHA-256 指纹。
- 电脑除 TLS 信任验证外，再按客户端证书 DER 内容计算 SHA-256，并要求它精确存在于已配对设备白名单。
- 没有客户端证书、证书未配对、证书变化或私钥不匹配时，不返回同步状态或账本摘要。
- 新增或移除设备后关闭旧监听并使用新白名单建立监听；旧连接不得继续获得新同步权限。
- 设备私钥丢失、App 重装或证书变化后必须重新配对。
- 当前完成 mTLS 传输基础和真实握手测试；已配对设备数据库表、配对提交接口和监听自动重启尚未接入。
- `flutter analyze` 无问题；完整 67 项自动测试、Windows 系统安全存储真实集成测试、Android Debug APK 和 Windows Debug 构建均通过。
