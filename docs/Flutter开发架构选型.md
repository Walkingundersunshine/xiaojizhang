## 1. 现在要决定什么

需要确定 App 内部如何组织页面、业务数据和 SQLite 数据库访问。这项选择不改变用户看到的功能，但会明显影响开发速度、出错概率、测试难度和以后增加功能的成本。

可以把三部分理解为：

- 状态管理：让“新增一笔花销”后，列表和统计能立即得到正确更新。
- 数据库访问层：负责把花销安全写入 SQLite，并读取、筛选和统计。
- 项目结构：决定代码按什么方式分组，避免功能增加后变得混乱。

## 2. 架构方案 1：Riverpod + Drift + 按功能分层

### 它是什么

Riverpod 负责管理页面使用的数据和操作状态；Drift 负责以类型安全的方式访问 SQLite；代码按“花销、分类、统计、设置”等产品功能分组，每个功能内部再区分界面、业务规则和数据访问。

类型安全的意思是：许多字段写错、类型不匹配和查询错误，可以在开发或构建阶段提前发现，而不是等用户运行 App 后才暴露。

### 优势

- 新增、修改或删除花销后，相关列表和统计容易自动刷新。
- Drift 与 SQLite 配合成熟，支持数据库版本迁移、复杂筛选和响应式查询。
- Riverpod 不依赖具体页面，业务逻辑比较容易单独测试。
- 按功能分层便于后续增加收入、预算、账户和移动端。
- 在开发效率、代码量和长期维护之间比较均衡。

### 劣势

- Riverpod 和 Drift 都需要一定学习成本。
- Drift 通常需要代码生成步骤；开发配置比直接写 SQL 多一些。
- 如果层次划分过细，会产生不必要的文件，因此需要控制首版结构规模。

### 成本与风险

- 初期搭建时间略多，但后续复杂查询和功能扩展的维护成本较低。
- 需要把生成代码纳入构建和测试流程，避免漏生成造成构建失败。

### 适合本项目的情况

希望首版开发稳妥，同时为以后增加统计、预算、账户或手机端留下扩展空间。

## 3. 架构方案 2：Bloc / Cubit + Drift + 严格分层

### 它是什么

Bloc / Cubit 把用户操作和界面状态按照较严格的流程组织；Drift 负责 SQLite；项目通常分为界面层、业务层和数据层，各层之间边界明确。

可以把它理解为一套更正式的管理制度：每次操作从哪里进入、经过哪些处理、最后如何更新页面，都有明确路径。

### 优势

- 数据变化过程清楚，复杂页面出现问题时比较容易追踪。
- 架构规则严格，适合较大的团队协作。
- 测试方法成熟，长期维护大型项目时可预测性较好。
- Drift 提供与方案 1 相同的数据库安全和迁移优势。

### 劣势

- 为简单功能也需要编写较多状态、事件或 Cubit 代码。
- 学习门槛和首版开发工作量高于方案 1。
- 对当前规模的个人记账 App，严格分层可能显得偏重。

### 成本与风险

- 前期设计和代码量最大。
- 如果未来没有发展成大型项目，部分架构投入可能无法体现价值。

### 适合本项目的情况

预期很快扩展为大型产品、多人团队长期协作，并愿意用更多首期开发成本换取严格规则。

## 4. 架构方案 3：Provider + ChangeNotifier + 直接访问 SQLite

### 它是什么

Provider 和 ChangeNotifier 用较简单的方式把数据通知给页面；通过桌面 SQLite 插件直接编写和执行 SQL；代码保持较少层次。

这是一套更直接的做法：需要什么功能就编写对应的页面逻辑和数据库语句，前期需要理解的概念较少。

### 优势

- 概念简单，最初搭建速度快。
- 第三方抽象较少，简单功能的代码路径直观。
- 可以直接控制 SQL，适合很小且长期不扩展的工具。

### 劣势

- SQL 字段、查询结果和 Dart 对象之间的转换需要手工维护，更容易出现遗漏。
- 新增或修改数据后，多个页面之间的同步刷新需要额外处理。
- 数据库升级和复杂统计增加后，维护成本上升较快。
- ChangeNotifier 的状态变化粒度较粗，功能变多后容易形成体积很大的管理类。

### 成本与风险

- 首期成本最低，但需求增长后返工和迁移风险最高。
- 金额、货币和分类属于需要高正确性的财务数据，手工映射必须投入更多测试。

### 适合本项目的情况

只追求很快做出小型原型，并且确定未来功能不会明显增加。

## 6. 我的建议

建议选择 **架构方案 1：Riverpod + Drift + 按功能分层**。

理由：

1. 记账数据需要可靠，Drift 能减少手写字段映射和数据库查询错误。
2. 花销列表、筛选结果和统计之间会共享数据，Riverpod 比简单通知机制更容易保持一致。
3. 当前项目还没有大到必须承担 Bloc 严格架构的额外代码量。
4. 未来如果增加收入、账户、预算或移动端，方案 1 不需要整体推倒重来。
5. 可以采用“轻量分层”，只建立当前确实需要的文件，避免为了架构而架构。

## 7. 选择后的实施范围

用户确认后，下一步只进行可运行的工程基础搭建，包括：

- 创建 Flutter 的 Windows 和 macOS 工程结构。
- 配置所选状态管理与 SQLite 访问依赖。
- 建立基础目录、代码规范和测试入口。
- 创建空白应用外壳并验证能通过静态检查和测试。

金额如何保存、分类数据表如何设计、界面采用哪种视觉风格，仍会分别提供方案，不会因为选择本架构而被自动决定。
