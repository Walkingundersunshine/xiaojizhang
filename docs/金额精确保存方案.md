# 晓记账：金额精确保存方案

| 项目 | 内容 |
| --- | --- |
| 决策编号 | T-003 |
| 日期 | 2026-07-29 |
| 当前状态 | 已选择方案 1 |

## 1. 要决定什么

决定每笔花销的金额在 SQLite 数据库中如何保存，确保长期统计不会出现小数误差。

## 2. 为什么现在要决定

金额字段是账目数据模型的核心。一旦用户产生真实数据，再更换保存方式就需要迁移所有账目，因此必须在创建数据库表之前确定。

不同货币的小数位数并不相同，例如：

- 人民币、美元通常为 2 位小数。
- 日元、韩元通常为 0 位小数。
- 科威特第纳尔等货币通常为 3 位小数。

## 3. 方案 1：按货币最小单位保存整数（推荐）

做法：数据库只保存整数金额，同时保存货币代码。人民币 `12.34` 元保存为 `1234` 分；日元 `500` 保存为 `500`；三位小数货币 `1.234` 保存为 `1234`。

优势：

- 加减和统计完全精确，不会产生浮点误差。
- SQLite 对整数求和、筛选和排序支持最好。
- 性能好，实现成熟，适合常见法定货币。
- 64 位整数能够覆盖个人记账所需的金额范围。

劣势和风险：

- 必须维护每种货币的小数位规则。
- 界面输入和显示时需要在整数与日常金额之间转换。
- 如果以后支持加密货币或超高精度资产，需要扩展方案。

成本：低，首版实现和长期维护都较简单。

## 4. 方案 2：以十进制文本保存

做法：把金额原样保存为文本，例如 `"12.34"`，在 Dart 中使用高精度十进制库计算。

优势：

- 可以支持任意小数位，扩展加密货币更容易。
- 不受 64 位整数最大值限制。
- 文本能保留用户输入的精度形式。

劣势和风险：

- SQLite 不能直接可靠地对文本金额求和和排序。
- 统计时需要读取更多数据到应用中计算，数据量大时更慢。
- 需要额外十进制计算依赖和更严格的格式校验。
- 查询、报表和数据库迁移更复杂。

成本：中到高。

## 5. 方案 3：使用普通小数类型 `REAL`

做法：直接把 `12.34` 作为数据库小数保存。

优势：

- 实现直观，SQLite 可以直接统计。
- 初期代码较少。

劣势和风险：

- 计算机二进制小数不能精确表示许多十进制金额。
- 大量加减后可能出现 `0.01` 级别或更小的统计误差。
- 对财务数据不够可靠，后期修正困难。

成本：初期低，但长期数据风险高。

## 6. 我的建议

建议选择 **方案 1：按货币最小单位保存整数**。当前产品范围是常用法定货币和个人花销记录，方案 1 在精确性、统计性能和维护成本之间最合适。数据库会同时保存 ISO 4217 货币代码，并由统一的货币规则表负责输入和显示转换。

如果未来决定支持比特币等高精度资产，再单独提出扩展方案，不影响首版常用货币记账。
