## 共同安全要求

无论选择哪种方案，首版都遵守以下规则：

1. 导出不改变 App 内的数据。
2. 恢复前先检查文件格式、版本和内容，不接受部分损坏的数据。
3. 恢复不会静默覆盖；必须显示将被替换的数据数量并再次确认。
4. 正式恢复前自动保存一份当前账本的安全备份；恢复失败时保留原数据。
5. 首版只支持“完整替换恢复”，暂不自动合并两个账本，避免重复账目和分类冲突。
6. 备份包含花销、分类、设置和必要的汇率数据；CSV 只用于查看和表格分析，不作为完整恢复文件。

## 方案 1：CSV 导出 + JSON 完整备份（推荐）

- 日常导出生成 UTF-8 CSV，可直接用 Excel、WPS 或 Numbers 打开。
- 完整备份生成一个带版本信息的 JSON 文件，包含全部账本数据。
- 恢复时先完整校验 JSON，再在数据库事务中一次性替换。

优势：

- CSV 方便普通用户查看和分析；JSON 适合可靠恢复，两种用途分开后不容易误用。
- JSON 不依赖当前数据库内部表结构，未来 App 升级时更容易兼容旧备份。
- 文件内容可检查，跨 Windows 和 macOS 迁移简单。
- 不需要引入 Excel 文件生成库，依赖和安装包增量较小。

劣势与成本：

- 完整备份文件通常比直接复制数据库略大，导入和导出也略慢。
- 需要编写严格的版本迁移、字段校验和异常回滚逻辑。
- JSON 文件可被手工修改，因此恢复时必须逐项校验，不能直接信任文件内容。

适合：重视长期兼容和跨系统迁移，希望导出文件容易查看，同时希望备份可稳定恢复。

## 方案 2：CSV 导出 + SQLite 数据库备份

- 日常导出仍使用 UTF-8 CSV。
- 完整备份直接复制 App 的 SQLite 数据库文件，或将数据库压缩成一个备份文件。

优势：

- 备份和恢复速度快，能精确保留当前数据库中的所有内容。
- 首版开发工作相对少，大数据量下性能最好。
- 备份文件通常比未压缩 JSON 小。

劣势与风险：

- 备份与数据库版本绑定较紧，未来表结构变化后，旧备份恢复更复杂。
- 复制数据库时必须正确处理数据库连接和临时日志，否则可能得到不完整文件。
- 用户无法直观检查备份内容，也不适合作为跨软件交换格式。
- 如果未来需要合并两个账本，直接数据库文件会更难处理。

适合：最重视开发速度和大数据量备份性能，可以接受未来升级时增加迁移维护成本。

## 方案 3：Excel 工作簿导出 + JSON 完整备份

- 导出生成 XLSX 工作簿，可把花销、分类和汇总放在不同工作表。
- 完整恢复仍使用带版本信息的 JSON 文件。

优势：

- 导出结果对 Excel/WPS 用户最友好，可包含多个工作表、格式和筛选表头。
- 分类表和花销表可以放在同一文件中，查看体验优于单个 CSV。
- JSON 备份仍能保持较好的未来版本兼容性。

劣势与成本：

- 需要增加 XLSX 生成依赖，安装包、开发量和跨平台测试范围都会增加。
- 文件格式更复杂，出现兼容问题时排查成本高于 CSV。
- 对只需要导出明细的首版而言，功能可能超过实际需要。

适合：明确需要经常在 Excel/WPS 中整理账本，并愿意接受更高开发和测试成本。

## 建议

建议选择方案 1。它让“给人看的导出”和“给 App 恢复的完整备份”各自使用合适的格式，在易用性、数据安全、长期维护和开发成本之间最均衡。

如果选择方案 1，下一步仍会把以下低一层细节列出并解释后再实施：备份文件扩展名、CSV 字段与多语言表头、恢复冲突提示和备份保存位置。

## 下一项决策：JSON 备份文件的封装方式

### 方案 1：自定义 `.jizhang` 文件，内容为普通 JSON（推荐）

- 用户看到的是一个名称明确的晓记账备份文件，例如 `晓记账备份-2026-07-30.jizhang`。
- 文件内部仍是标准 UTF-8 JSON，必要时可用文本编辑器检查。

优势：容易和普通 JSON、CSV 文件区分；不需要压缩依赖；Windows 与 macOS 都能直接读写；未来可以让系统把该扩展名关联到晓记账。

劣势：其他软件不会自动识别 `.jizhang`；文件仍可被手工修改，所以恢复时必须严格校验。

### 方案 2：标准 `.json` 文件

- 文件名例如 `晓记账完整备份-2026-07-30.json`。

优势：格式最透明，文本编辑器和开发工具都能直接识别；无需自定义扩展名说明。

劣势：容易和其他 JSON 文件混淆，也更容易被用户误编辑；文件选择窗口不容易一眼区分普通 JSON 与有效账本备份。

### 方案 3：压缩的 `.jizhang` 文件

- `.jizhang` 实际为 ZIP，内部包含 `backup.json`、版本清单和校验信息。

优势：文件更小；未来可加入附件或多份数据文件；内部清单和校验文件更灵活。

劣势：需要增加压缩依赖和更多损坏处理逻辑；用户无法直接查看内容；对当前没有图片附件的首版而言复杂度偏高。

建议选择方案 1，在辨识度、透明性、跨平台和实现成本之间最均衡。

## 下一项决策：CSV 字段与表头形式

### 方案 1：面向普通用户的中文明细（推荐）

- 使用中文表头：金额、货币、一级分类、二级分类、发生时间、时区、备注、创建时间、更新时间。
- 金额使用正常小数形式，例如 `12.50`，不暴露数据库内部的最小单位整数。
- 文件采用带 UTF-8 BOM 的标准逗号分隔格式，提升 Windows Excel 正确识别中文的成功率；字段内的逗号、引号和换行会按 CSV 规则转义。

优势：Excel、WPS 和 Numbers 打开后最容易理解；表格简洁；符合 CSV 只用于查看和分析、不用于完整恢复的定位。

劣势：不包含内部分类 ID、金额整数和 UTC 毫秒等技术字段，不适合其他程序精确导入。

### 方案 2：面向程序处理的英文技术字段

- 使用固定英文表头，并导出记录 ID、金额最小单位整数、分类 ID、UTC 时间和时区偏移等原始字段。

优势：字段稳定、信息精确，适合脚本分析或将来制作导入工具。

劣势：普通用户难以阅读；直接在 Excel 中分析金额和时间前需要转换；与完整备份功能存在一定重复。

### 方案 3：中文展示字段 + 技术字段全部导出

- 同时保留正常金额、中文分类和内部 ID、整数金额、UTC 时间等字段。

优势：信息最完整，既方便查看，也给高级用户保留程序处理能力。

劣势：列数多且内容重复，普通用户容易困惑；用户修改后也不能直接作为安全的恢复文件。

建议选择方案 1。完整、精确、可恢复的数据已经由 `.jizhang` 备份承担，CSV 保持清晰易读更符合两种文件的用途分工。

### 已确定的 CSV 字段

CSV 使用固定英文表头，首版字段顺序如下：

1. `expense_id`
2. `amount_minor`
3. `currency_code`
4. `parent_category_id`
5. `parent_category_name`
6. `category_id`
7. `category_name`
8. `occurred_at_utc_milliseconds`
9. `occurred_timezone_offset_minutes`
10. `note`
11. `created_at_utc_milliseconds`
12. `updated_at_utc_milliseconds`

文件采用 UTF-8、逗号分隔和标准 CSV 引号转义。英文表头不需要 BOM 才能识别；为了兼容备注和分类中的中文，首版仍写入 UTF-8 BOM，降低 Windows Excel 误判编码的概率。以 `=`、`+`、`-`、`@`、制表符或回车开头的文本会增加单引号安全前缀，避免 Excel/WPS 将用户文本当作公式执行。CSV 不作为恢复入口，未改变的原始文本保存在 `.jizhang` 完整备份中。

## 下一项决策：恢复现有账本的处理方式

### 方案 1：只支持完整替换，并自动创建恢复前备份（推荐）

- 校验通过后，用备份内容完整替换当前花销、分类、设置和必要汇率数据。
- 替换前自动生成当前账本的 `.jizhang` 安全备份；恢复失败则回滚，不改变当前数据。

优势：结果清楚，不会产生重复账目或分类冲突；实现与测试范围可控；出现误操作时可以用自动备份撤销。

劣势：不能直接把两台电脑上的账本合并；用户必须明确理解当前数据会被替换。

### 方案 2：只支持合并恢复

- 根据记录和分类 ID 合并备份与当前账本；遇到相同 ID 时需要决定保留哪一份。

优势：可以汇集不同电脑上的记录，当前账本不会整体被替换。

劣势：同一笔记录被分别修改、分类同名不同 ID、设置不一致时很难自动判断；容易产生重复数据；开发和测试成本明显更高。

### 方案 3：同时提供完整替换和合并恢复

- 恢复时由用户选择模式，并为合并冲突提供处理规则。

优势：功能最完整，既能迁移整本账，也能汇集多个账本。

劣势：恢复界面和测试范围最大；普通用户更容易选错模式；首版交付时间更长。

建议选择方案 1。首版先保证恢复行为可预测、失败可回滚；账本合并可在未来单独设计去重和冲突规则后增加。

## 下一项决策：手动导出与备份的保存位置

恢复前由 App 自动生成的安全备份不弹出保存窗口，固定放在 App 私有数据目录的 `recovery-backups` 子目录中，避免用户取消保存后失去回滚保障。以下选择只决定用户主动导出 CSV 和创建 `.jizhang` 备份时的行为。

### 方案 1：每次使用系统“另存为”窗口（推荐）

- 用户每次选择文件名和保存文件夹。
- 默认文件名带日期时间，例如 `expenses-2026-07-30-143000.csv` 和 `jizhang-backup-2026-07-30-143000.jizhang`。

优势：保存位置清楚，可直接选择移动硬盘、网盘或指定文件夹；符合 Windows 与 macOS 的常见桌面软件习惯；App 不需要长期保存文件夹权限。

劣势：每次都多一步确认；频繁备份时操作略慢。

### 方案 2：固定保存到“文档/晓记账”文件夹

- App 自动创建并使用系统文档目录下的专用文件夹，不再每次询问。

优势：操作最快，所有导出文件集中管理；适合经常手动备份。

劣势：用户可能不知道文件保存到了哪里；文档目录被网盘同步或受企业策略管理时行为可能不同；同名和旧文件清理需要额外规则。

### 方案 3：在设置中选择默认文件夹

- 第一次使用时选择文件夹，此后自动保存；设置页可以更改。

优势：兼顾操作速度和位置控制，适合长期固定备份到移动盘或网盘目录。

劣势：需要保存并验证目录权限；移动盘断开、目录删除或 macOS 权限失效时需要重新选择；设置和错误处理更复杂。

建议选择方案 1。首版行为最直观，跨平台权限问题最少，也不会让用户误以为文件已经自动保存在某处。

## 下一项决策：系统文件窗口技术组件

### 方案 1：Flutter 官方维护的 `file_selector`（推荐）

- 使用 Windows 和 macOS 的原生打开、另存为窗口。
- 由 Flutter 官方 `flutter/packages` 仓库维护，支持桌面文件类型筛选和建议文件名。

优势：来源和维护责任清楚；API 范围聚焦；与当前 Flutter 技术栈一致；不需要自行编写 Windows 和 macOS 原生代码。

劣势：只负责选择路径和文件，备份校验、实际读写、覆盖确认仍需 App 自己实现；高级文件窗口定制能力有限。

### 方案 2：社区维护的 `file_picker`

- 提供跨平台文件和目录选择，也支持保存文件窗口。

优势：功能更广，社区使用量较大；未来如果增加批量文件或目录选择，可继续使用同一组件。

劣势：首版会引入超出当前需求的能力；桌面各平台行为和版本兼容依赖社区维护；升级时需要关注更广的平台代码变化。

### 方案 3：自行编写 Windows/macOS 原生文件窗口代码

- Windows 使用原生文件对话框，macOS 使用系统面板，通过 Flutter 平台通道连接。

优势：控制能力最强，可以精确调整平台行为且不增加第三方文件选择依赖。

劣势：必须维护两套原生实现；需要分别在 Windows 与 macOS 编译测试；开发和长期维护成本最高。

建议选择方案 1。它覆盖当前打开备份、另存 CSV 和另存备份的全部需求，依赖来源也最稳妥。
