## 1. 要决定什么

决定如何处理当前项目路径 `E:\记账App` 与 Flutter/Dart 工具之间的兼容问题。

## 2. 为什么现在要决定

Windows 开发者模式已经成功开启，`flutter pub get` 也曾成功完成，但后续验证暴露出两个与路径有关的异常：

- `flutter analyze` 在处理包含 `E:\记账App` 的工作区 URI 时，分析服务返回被截断的数据并报 `FormatException: Unexpected end of input`。
- Flutter 命令在当前路径下偶尔长时间等待，影响 `analyze`、`test` 和 Windows 构建验证。

在这个问题解决前继续编写数据库和业务代码，会失去可靠的自动检查，不适合进入正式功能开发。

## 3. 方案 1：保留原目录，使用英文盘符映射（推荐先验证）

做法：保留 `E:\记账App` 不动，在每次开发时把它映射为一个简短英文盘符，例如 `J:\`，并从 `J:\app` 打开 VS Code 和运行 Flutter。

优势：

- 不移动现有文件，当前中文目录仍然保留。
- 改动小，验证失败时可立即取消映射。
- 如果 Flutter 在 `J:\app` 下通过分析和构建，可以较快继续开发。

劣势和风险：

- 电脑重启后通常需要重新建立映射，可以用一个本地脚本简化。
- 必须统一从映射后的路径打开项目；中文路径和映射路径混用可能让编辑器缓存混乱。
- 它属于兼容绕行方案，并没有消除原始中文路径。

成本：低，预计几分钟完成首次验证。

## 4. 方案 2：迁移到纯英文目录

做法：把整个项目迁移为纯英文路径，例如 `E:\jizhangben`，以后直接从新路径开发。

优势：

- 从根源上避开多数开发工具的中文路径兼容问题。
- 不需要每次建立盘符映射，长期维护最简单。
- CI、脚本和第三方构建工具通常对纯英文路径支持更稳定。

劣势和风险：

- 项目位置会变化，VS Code 最近项目、终端命令和已有链接需要更新。
- 迁移前后必须检查 Git 状态和文件完整性。
- 用户习惯的中文文件夹名称会改变。

成本：中等，一次性迁移和完整复验预计需要十几分钟。

## 5. 方案 3：保持现状，等待 Flutter/Dart 修复

做法：继续使用 `E:\记账App`，暂不采取兼容措施。

优势：

- 不改变路径，也不增加盘符映射。

劣势和风险：

- 当前无法可靠运行代码分析、测试和 Windows 构建验证。
- 修复时间不可确定，可能长期阻塞开发。
- 继续开发会积累未经自动检查的代码，返工风险较高。

成本：眼前最低，但延期和返工风险最高。

## 6. 我的建议

建议先选择 **方案 1**。它不移动任何文件，能用最低成本确认英文路径是否确实解决问题。如果验证后仍不稳定，再向用户报告证据并重新决定是否采用方案 2。
