## 1. 要决定什么

决定 Windows 测试和构建时如何取得 SQLite 原生运行库。

## 2. 为什么现在要决定

项目迁移到 `E:\jizhang` 后，`flutter analyze` 已通过，证明中文路径问题已解决。随后运行 `flutter test` 时，`sqlite3` 依赖尝试从其官方 GitHub Release 下载：

`sqlite3.x64.windows.dll`

当前网络连接 GitHub 超时，因此原生资产构建失败，测试代码尚未开始执行。

默认下载并不是未知文件：`sqlite3` 包中内置了对应文件的 SHA-256，下载完成后会自动比对；哈希不一致时构建会失败。

## 3. 方案 1：继续使用官方 GitHub 文件并重试（推荐）

做法：保持默认配置，重新下载官方 Release 中的 DLL；必要时通过浏览器手动取得同一个官方文件，再让构建使用本地缓存。

优势：

- 来源是 `sqlite3.dart` 项目自己的官方 Release。
- 依赖包会自动进行 SHA-256 校验，供应链风险最低。
- Windows 和 macOS 使用同一套官方编译选项，功能最一致。
- 不需要修改应用代码或长期维护自定义配置。

劣势和风险：

- 当前网络到 GitHub 不稳定，可能需要多次重试或手动下载。
- 首次准备时间不可完全预测。

成本：低；下载成功后后续可复用缓存。

## 4. 方案 2：配置第三方或自建镜像

做法：在 `pubspec.yaml` 中配置 `url_pattern`，让构建从指定镜像下载同名 DLL。

优势：

- 如果镜像在国内访问稳定，首次构建更快。
- 依赖包仍会使用内置 SHA-256 校验文件内容。

劣势和风险：

- 必须先确定可信、长期稳定的镜像来源，目前项目没有已审核的镜像。
- 镜像可能停止服务或同步不及时，形成新的第三方依赖。
- 需要维护额外构建配置。

成本：中等，需要筛选和验证镜像。

## 5. 方案 3：使用系统 SQLite 或自行从源码编译

做法：Windows 使用系统自带的 `winsqlite3`，macOS 使用系统 `sqlite3`；或者把官方 `sqlite3.c` 放进项目并在构建时自行编译。

优势：

- 系统库方式不需要下载 GitHub 预编译 DLL。
- 源码编译方式可以完全控制 SQLite 版本和编译选项。

劣势和风险：

- Windows 与 macOS 系统库的版本和功能选项可能不同，跨平台行为不完全一致。
- 系统库可能较旧，全文搜索、数学函数等功能未必一致。
- 源码编译会增加仓库内容、构建时间和长期维护工作。
- 对当前晓记账首版来说复杂度明显偏高。

成本：系统库为中等，源码编译为高。

## 6. 我的建议

建议选择 **方案 1**。官方文件加包内 SHA-256 校验最符合项目对数据可靠性和供应链安全的要求。当前问题是网络超时，不是文件或架构不兼容；优先解决一次性下载，比长期引入镜像或平台差异更稳妥。
