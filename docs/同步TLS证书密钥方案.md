## 要决定什么

每台设备生成自签名 TLS 证书时使用哪种密钥，以及由谁负责生成。

## 方案 1：ECDSA P-256 证书，由 App 本地生成（推荐）

App 首次启用同步时在本机生成一把 ECDSA P-256 私钥和自签名证书，私钥立即写入系统安全存储，公开证书用于二维码指纹和设备配对。

优势：密钥和证书体积小；生成和握手速度快，适合手机；Android 10、现代 Windows/macOS 和当前 TLS 均广泛支持；不依赖外部命令行程序。

劣势：需要选择并审查能正确生成 X.509 证书的 Dart 组件；旧式 TLS 工具兼容性不如 RSA，但不影响本项目已确定的系统范围。

成本和风险：开发成本居中；必须使用系统安全随机数和成熟密码库，不能自行实现椭圆曲线算法。

## 方案 2：RSA 3072 位证书，由 App 本地生成

App 在本机生成 RSA 3072 位私钥和自签名证书，再写入系统安全存储。

优势：TLS 和证书工具兼容性非常广；资料和排错工具较多；实现概念成熟。

劣势：密钥和二维码相关公开数据更大；手机首次生成密钥较慢；握手计算量高于 ECDSA；对本项目现代系统范围没有明显收益。

成本和风险：开发成本居中；生成期间需要避免界面卡顿，仍必须使用成熟密码库和安全随机数。

## 方案 3：分别调用 Android、Windows、macOS 原生密钥与证书接口

为三个系统分别编写原生代码，让操作系统生成并管理证书密钥，尽量使私钥不可导出。

优势：与各系统安全能力结合最深；部分平台可让私钥保持不可导出；长期安全边界最好。

劣势：需要 Kotlin、C++/Windows API 和 Swift 三套实现；行为和备份规则不同；跨平台测试量最大；当前 Windows 无法完成 macOS 原生实现验证。

成本和风险：开发和维护成本最高，交付时间最长；任一平台实现错误都会造成无法重新连接或升级。

## 我的建议

建议选择方案 1。ECDSA P-256 是现代 TLS 的成熟选择，适合 Android 手机，证书小、生成快；配合系统安全存储和证书指纹固定，能够满足当前个人局域网同步范围。

## 兼容验证结果

已对候选 Dart 组件 `basic_utils 5.8.2` 进行实际代码验证，而不是只依据其文档：

- 组件能够生成 ECDSA P-256 密钥、CSR 和自签名证书，也能用自身解析该证书。
- 将生成的 ECDSA 证书交给 Flutter `SecurityContext` 时，Flutter 内置 BoringSSL 返回 `CANNOT_PARSE_LEAF_CERT / UNKNOWN_CERTIFICATE_TYPE`，不能建立 TLS 服务。
- 不能通过“忽略证书错误”解决，因为错误发生在本机证书载入阶段，而且忽略校验会违反已经确定的证书指纹固定要求。
- 同一组件生成的 RSA 3072 位证书和私钥已实测能够成功载入 Flutter `SecurityContext`。
- 实验性 ECDSA 实现和临时测试文件已从项目中移除，不提交无法工作的安全代码。

## 新证据后的重新选择

### 新方案 1：改用 RSA 3072 位本地证书（推荐）

采用原方案 2。Flutter TLS 实测已经通过，仍使用系统安全存储保护私钥，并继续严格固定证书指纹。

优势：当前技术栈已经验证可用；不需要三套原生实现；TLS 兼容成熟；可以继续开发。

劣势：证书和私钥比 ECDSA 大，手机首次生成略慢，但只在首次启用同步或重新配对身份时发生。

### 新方案 2：坚持 ECDSA，改用三平台原生密钥与证书接口

Android、Windows、macOS 分别实现原生证书生成，再交给 Flutter TLS 使用。

优势：可以保留 ECDSA，并有机会使用平台硬件或不可导出密钥能力。

劣势：需要三套原生开发；Windows 当前只能验证两端中的 Windows/Android，macOS 仍需 Mac；开发周期和维护成本最高。

### 新方案 3：暂停局域网 TLS 同步

保留现有本地账本和手动备份功能，等待出现经 Flutter/BoringSSL 实测兼容、维护状态可靠的 ECDSA 证书组件后再继续。

优势：不为赶进度降低安全要求，也不立即承担三平台原生实现成本。

劣势：Android App 可以继续开发，但局域网同步无法按当前计划交付，等待时间不确定。

## 更新后的建议

建议选择新方案 1：RSA 3072 位。它已通过当前 Flutter TLS 的实际载入测试，安全边界和证书指纹固定规则不变，性能差异只影响极少发生的首次密钥生成。
